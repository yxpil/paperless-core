# 06 老设备与传统无纸化对接

## 6.1 老设备到底难在哪

「老设备接入」听起来是兼容性问题，实际上是四类完全不同的问题，必须分别对待。把它们混成一句话，方案就会变成「换设备吧」。

| 类型 | 特征 | 难点 | 应对 |
| --- | --- | --- | --- |
| A 计算弱 | 内存 < 2 GB，浏览器内核老旧 | 跑不动现代 Web | 降级为薄客户端或外挂显示 |
| B 系统旧 | Win7/XP、老 Android 4.x | TLS 1.3、现代 JS 全不支持 | 网关终结加密，向下用兼容协议 |
| C 无网络 | 只有串口、红外、GPIO | 无法 IP 直达 | 边缘网关做协议翻译 |
| D 专有协议 | 厂商私有，无文档 | 需要逆向或厂商配合 | 抓包分析 + 协议插件 |

判断一台设备属于哪类，用三个问题：能不能装我们的客户端？能不能建立 TLS？能不能自己发网络包？三个都否，就落到「外挂显示 + 硬件采集」这条兜底路。

## 6.2 五级接入模型

| 级别 | 名称 | 做法 | 体验 | 成本 |
| --- | --- | --- | --- | --- |
| L0 | 原生 | 装官方客户端 | 完整 | 低 |
| L1 | 降级 | 装精简客户端，关闭视频与协作 | 阅读+同屏+表决 | 低 |
| L2 | 显示 | 网页只读 + 受控浏览器 | 只读、跟随主控 | 中 |
| L3 | 硬件 | HDMI 采集 + 网关编码 + 反向红外控制 | 只读画面 | 中高 |
| L4 | 不可改造 | 人工旁路：纸质签到补录、场外直播 | 旁听 | 高（人工） |

选级原则：**能用 L1 不用 L3，能用 L3 不用 L4**。L4 不是技术方案，是承认失败后的兜底，必须在项目启动时就告知客户哪些设备无法接入。

## 6.3 边缘网关

网关是 L1–L3 的物理承载，一台设备服务一个会议室。

| 项 | 规格 |
| --- | --- |
| 主控 | ARM64 四核，2 GB 内存，16 GB eMMC |
| 网络 | 双网口（内外网隔离），可选 4G/5G 备份 |
| 工业接口 | RS-485 × 1、RS-232 × 1、红外发射 × 1、GPIO × 4 |
| 供电 | PoE 或 12 V DC |
| 系统 | 只读根文件系统 + 双分区 A/B 升级 |
| 断网能力 | 本地缓存最近一场材料，断网续会 30 分钟 |
| 安全 | 出厂证书 + 首次启动绑定 + 安全启动 |

网关的软件栈四层：接入层（MQTT over TLS 到中心）、协议层（驱动插件）、缓存层（SQLite + 文件）、编排层（本地场景执行）。断网时编排层仍能跑已下发的场景，这是「断网也能开会」的关键。

## 6.4 对接传统无纸化会议系统

客户往往已经有旧系统在跑（升降、话筒、投票、桌牌）。替换不能一刀切，正确姿势是**影子运行**：新系统并行上线，旧系统继续服务，直到验证通过再切。

| 阶段 | 做法 | 判定 |
| --- | --- | --- |
| 只读镜像 | 从旧系统数据库/接口同步会议与人员，新系统只读展示 | 数据一致率 ≥ 99% |
| 双写观察 | 新系统写自己的库，同时向旧系统发同样的指令，比对执行结果 | 指令一致率 ≥ 98%，差异可解释 |
| 主备切换 | 新系统为主，旧系统为备，异常时一键回切 | 连续 10 场无故障 |
| 退役 | 旧系统只保留硬件控制通道 | 客户签署确认 |

对接方式按可得性排序：

| 旧系统能力 | 对接方式 | 说明 |
| --- | --- | --- |
| 有开放 API | 服务插件直接调用 | 最理想，需厂商配合 |
| 有数据库只读权限 | 数据源插件 + CDC | 注意不要写旧库 |
| 只有文件交换 | 定时导入导出 | 延迟大，适合非实时数据 |
| 只有界面 | L3 采集 + 红外/串口控制 | 兜底，体验受限 |

一个必须写进合同的条款：**旧系统的数据库结构变更必须提前通知**。实践中大量对接事故来自厂商升级改了字段，同步任务静默失败。

## 6.5 协议插件示例

以升降与桌牌为例，协议插件把 MQTT 指令翻译成串口帧：

```ts
import { definePlugin, z } from '@paperless/plugin-sdk';

const CMD = { screenDown: 0x11, screenUp: 0x12, nameplateWrite: 0x21 } as const;

export default definePlugin({
  id: 'com.example.legacy-rs485',
  commands: {
    'device.command': {
      input: z.object({ deviceId: z.string(), cmd: z.string(), args: z.record(z.any()).optional() }),
      async handler(input, ctx) {
        const dev = await ctx.device.resolve(input.deviceId);
        if (!dev?.port) throw ctx.error('DEV_NOT_BOUND', 404);
        const frame = buildFrame(CMD[input.cmd], input.args);
        await ctx.uart.write(dev.port, frame, { timeoutMs: 2000 });
        const ack = await ctx.uart.read(dev.port, { timeoutMs: 2000 });
        if (!ack.ok) {
          await ctx.audit.record('device.command.failed', { deviceId: input.deviceId, cmd: input.cmd });
          throw ctx.error('DEV_NO_ACK', 502);
        }
        return { ok: true };
      },
    },
  },
});

function buildFrame(op: number, args?: Record<string, unknown>) {
  const payload = op === CMD.nameplateWrite ? Buffer.from(String(args?.text ?? ''), 'utf8') : Buffer.alloc(0);
  const head = Buffer.from([0xAA, 0x55, op, payload.length]);
  const sum = [...head, ...payload].reduce((a, b) => (a + b) & 0xff, 0);
  return Buffer.concat([head, payload, Buffer.from([sum])]);
}
```

校验位算法、超时、重试次数都写在插件配置里，不同厂商不同，不做全局假设。

## 6.6 兼容测试

| 用例 | 内容 | 通过标准 |
| --- | --- | --- |
| AC-01 | L1 降级客户端入会 | 8 秒内进入待机页，翻页 ≤ 800 ms |
| AC-02 | L2 网页只读 | 30 秒内加载，跟随翻页误差 ≤ 1 页 |
| AC-03 | L3 采集投屏 | 首帧 ≤ 3 秒，延迟 ≤ 800 ms，连续 2 小时不断流 |
| AC-04 | 断网续会 | 拔网线后 30 分钟内可继续翻页与批注 |
| AC-05 | 协议指令 | 20 条指令全部有 ACK，失败可重试 |
| AC-06 | 旧系统双写 | 连续 10 场指令一致率 ≥ 98% |

测试必须在真机做。模拟器只能验证协议，验证不了「老机器解码 4 Mbps 视频会不会卡」。

## 6.7 风险清单

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 厂商拒绝提供协议 | 无法做 L3 以上接入 | 提前在商务层面约定开放义务 |
| 设备固件升级改协议 | 插件失效 | 版本探测 + 兼容分支 + 灰度 |
| 老设备无备件 | 单点故障 | 关键会议室备机 |
| L4 比例过高 | 客户体验落差 | 立项时明确清单，写入验收范围 |
| 采集卡兼容性 | 黑屏、分辨率不识别 | 出兼容清单，只支持清单内型号 |
