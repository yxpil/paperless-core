# 05 多设备联动与投屏远程控制

## 5.1 联动的三个层次

「多设备联动」在需求里常常是一句话，工程上是三件不同的事。必须分层实现，否则会互相打架。

| 层次 | 含义 | 例子 | 技术依赖 |
| --- | --- | --- | --- |
| 会话联动 | 同一房间内所有端共享同一 rev | 主持人翻页，全场同步 | 事件总线 + rev 定序 |
| 场景联动 | 一组设备按角色协同动作 | 签到 → 亮桌牌 → 降屏 → 开材料 | 编排引擎 + 设备影子 |
| 编排联动 | 跨房间、跨系统按条件触发 | 主会场闭会 → 分会场自动开场 | 规则引擎 + 插件能力 |

三层共用一个事件模型，区别只在于事件的「作用域」：`room`、`device`、`system`。

## 5.2 会话协议

事件信封固定八个字段，任何一端都不得裁剪：

```json
{
  "v": 1,
  "rev": 10237,
  "type": "material.page.changed",
  "roomId": "r-8f21",
  "ts": "2026-11-05T06:12:33.412Z",
  "from": "d-2a91",
  "opId": "op-5c33e1",
  "payload": { "materialId": "m-77", "page": 12 }
}
```

| 字段 | 作用 | 错用后果 |
| --- | --- | --- |
| `v` | 协议版本 | 版本不一致导致解析失败 |
| `rev` | 单调递增，唯一顺序依据 | 用 `ts` 排序必错，因为时钟有偏差 |
| `type` | 事件类型，命名 `域.对象.动作` | 命名混乱导致订阅错乱 |
| `opId` | 幂等键，重试去重 | 重复应用导致白板重影 |
| `from` | 来源终端 | 无法定位异常终端 |

rev 由 Redis Lua 原子分配（INCR + XADD 同一脚本内完成），保证「分配顺序 = 广播顺序」。断线重连时终端带 `lastRev` 补拉，窗口 2000 条；超出窗口下发 `view.snapshot` 全量快照。

## 5.3 主持人模型与分组

| 角色 | 权限 | 边界 |
| --- | --- | --- |
| 主持人 | 控议程、控同屏、发起表决、分组、移出成员 | 不能删除他人批注、不能改材料原件 |
| 联席主持 | 在主持人授权下代管某段议程 | 授权到期自动收回 |
| 主讲人 | 控制当前材料与投屏 | 仅限被指派的材料 |
| 参会人 | 阅读、批注、表决、举手 | 无控制权 |
| 观察员 | 只读，可看直播 | 无水印豁免 |
| 列席 | 只读 + 可被点名发言 | 无表决权 |

分组是把一个房间拆成多个子房间。子房间有独立的 rev 空间与事件通道，父房间只接收各子房间的「摘要事件」（如「第 3 组已形成结论」）。这样设计的原因是：分组讨论的内容量很大，若全部汇入父房间，父房间的 rev 会被冲垮，且参会人会被无关事件淹没。

分组规则支持三种：按部门、按人员名单、随机均分。主持人可在会议中动态调整，调整动作本身是一条 `room.group.changed` 事件，可溯源。

## 5.4 投屏的三条通道

投屏不是一种技术，是三种，按内容类型选择：

| 通道 | 原理 | 适用 | 带宽（1080p） | 延迟 |
| --- | --- | --- | --- | --- |
| 文档级 | 服务端渲染页帧，终端只收页号与图层 | 平台内材料、PDF/PPT/Excel | 1–3 KB/次翻页 | ≤ 300 ms |
| 应用采集 | 客户端采集窗口/屏幕，编码为视频流 | 第三方应用、浏览器、开发工具 | 1.5–4 Mbps | 200–500 ms |
| 硬件采集 | 采集卡/HDMI 环出，网关编码 | 老设备、无客户端的主机 | 2–6 Mbps | 300–800 ms |

选择逻辑由客户端自动判定：内容在平台内 → 文档级；窗口属于本机第三方应用 → 采集；信号来自外部主机 → 硬件。用户不需要理解差别，只需点「投屏」。

文档级通道是平台的护城河：300 页材料全程翻一遍，总流量不到 1 MB，而视频通道要几百 MB。这不是优化，是数量级差异。

投屏内容在屏幕上如何与其他资源共处（画中画、分屏、材料上叠白板），由第 20 章的图层模型统一决定。投屏只负责「把内容送到」，叠放负责「怎么摆」。

## 5.5 投屏远程控制

远程控制是投屏的反向通道：观看端可以操作投屏源的界面。这是高风险能力，必须四道锁。

| 锁 | 机制 |
| --- | --- |
| 授权 | 投屏方显式开启「允许远程控制」，默认关闭；开启时弹出确认 |
| 范围 | 只允许控制被投屏的那个窗口，不允许控制整机 |
| 身份 | 只有主持人或被指派的协助者可控制，且需二次确认 |
| 审计 | 每次点击、每次输入都记录（输入内容只记长度与类型，不记明文） |

技术实现：采集端注入一个轻量输入代理，接收观看端的坐标与键值事件，转换为系统输入。Windows 走 `SendInput`，macOS 走 `CGEvent`，Linux 走 `uinput`。这条路径天然敏感，因此在国产化与涉密环境中默认禁用，由策略开关控制。

必须说明的边界：远程控制无法做到「只让对方看到我想让他看到的」。一旦允许控制，对方理论上可以打开该窗口内的任意内容。因此平台在开启时强制把该窗口的标题与缩略图展示给投屏方确认。

## 5.6 弱网与降级

| 网络状况 | 判定 | 策略 |
| --- | --- | --- |
| 优 | RTT < 80 ms，丢包 < 1% | 全功能，视频 1080p30 |
| 良 | RTT < 200 ms，丢包 < 5% | 视频降 720p，文档级不受影响 |
| 差 | RTT < 500 ms，丢包 < 15% | 关视频，只保文档级 + 文字聊天 |
| 极差 | 丢包 > 15% 或频繁断连 | 转离线模式，本地缓存 + 事后补同步 |

降级由客户端上报质量指标、服务端统一下发策略，避免各端各自判断导致体验割裂。

## 5.7 场景编排

设备联动靠脚本，不靠人工。场景定义是可版本化的 YAML，由编排引擎执行，每步可设超时与失败策略。

```yaml
id: scene.board-meeting
name: 董事会开场
trigger: { type: room.state, from: READY, to: LIVE }
steps:
  - device.command: { target: group:main-room, cmd: screen.down, timeoutMs: 8000, onFail: continue }
  - device.command: { target: group:main-room, cmd: nameplate.show, args: { text: "${attendee.name}" } }
  - room.action: { action: material.open, materialId: "${agenda.current}" }
  - room.action: { action: vote.prepare, voteId: "v-kickoff" }
```

`onFail` 三档：`continue`（继续）、`retry`（重试 3 次）、`abort`（终止并告警）。选择哪一档要看这一步失败会不会影响会议进行：降屏失败可以继续，打开材料失败必须告警。

## 5.8 时钟与对齐

同屏一致性的前提是时间可比。所有终端启动时与边缘网关做一次 NTP 校时，目标偏差 ≤ 100 ms；会议中每 10 分钟复校一次。视频通道用 RTCP 做媒体内同步，文档通道靠 rev 而非时间，因此时钟偏差不会导致文档错位——这正是用 rev 定序的价值。

## 5.9 关键指标

| 指标 | 目标 | 采集点 |
| --- | --- | --- |
| 同屏延迟 P95 | ≤ 300 ms | 服务端广播时间 vs 终端应用时间 |
| 投屏首帧 | ≤ 1.5 s | 点击到首帧渲染 |
| 远程控制响应 | ≤ 120 ms | 事件发出到对端执行 |
| 事件丢失率 | 0（靠补拉保证） | rev 连续性校验 |
| 场景执行成功率 | ≥ 98% | 编排引擎 |
