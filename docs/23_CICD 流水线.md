# 23 CI/CD 流水线

## 23.0 五条原则

| 原则 | 含义 | 反例 |
| --- | --- | --- |
| 一切即代码 | 构建、部署、配置、迁移全部版本化 | 手工改服务器配置 |
| 可重复构建 | 同一 commit 在任何机器产出同一制品 | 「我本地能跑」 |
| 快速反馈 | PR 反馈 10 分钟内给到 | 等 40 分钟才知道编译失败 |
| 主干开发 | 短分支、小 PR、频繁合入 | 长分支合入地狱 |
| 永远可回滚 | 每次发布都有确定的回退路径 | 发上去就下不来 |

流水线的价值不是「自动跑测试」，而是**把发布这件高风险动作变成低风险的日常动作**。判断标准很朴素：一天能发几次？发挂了多久能恢复？

## 23.1 总览

```mermaid
flowchart LR
  A[push / PR] --> B[L0 静态检查]
  B --> C[L1 单元测试]
  C --> D[L2 契约与集成]
  D --> E[L3 构建与签名]
  E --> F[L4 端到端]
  F --> G[L5 性能冒烟]
  G --> H[L6 安全扫描]
  H --> I[制品库]
  I --> J[自动部署 Staging]
  J --> K[手动审批]
  K --> L[生产金丝雀 5%]
  L --> M[全量 / 回滚]
```

L0–L2 是 PR 门禁（阻塞合并），L3–L6 是合并后流水线（阻塞发布），部署段受审批控制。

## 23.2 分支与触发

| 事件 | 触发内容 | 时长预算 |
| --- | --- | --- |
| PR 创建/更新 | L0–L2 + 受影响包的测试 | ≤ 10 分钟 |
| 合入 main | L0–L6 全量 + 制品 | ≤ 40 分钟 |
| 打 tag `v*` | 全量 + 生产制品 + 发布单 | ≤ 60 分钟 |
| 定时（每日 02:00） | 全量 + 依赖扫描 + 存量镜像重扫 | — |
| 手动 | 指定环境部署、回滚 | — |

分支模型：主干 `main` + `feat/*`（存活 ≤ 3 天）+ `release/*`（冻结期）。禁止长期存在的 `develop`。

PR 规则：单 PR 改动 ≤ 400 行（不含生成代码与锁文件），超过需拆分说明。这条规则对评审质量的影响大于任何评审模板。

## 23.3 分阶段设计

### L0 静态检查（≤ 90 秒）

| 检查 | 工具 | 失败处理 |
| --- | --- | --- |
| 格式与 lint | ESLint + Prettier | 阻断 |
| 类型 | `tsc --noEmit` | 阻断 |
| 依赖方向 | dependency-cruiser | 阻断 |
| 复杂度 | 圈复杂度 > 15 报警 | 警告（进指标） |
| 许可证 | license-checker，禁 GPL | 阻断 |
| 密钥扫描 | gitleaks | 阻断并通知 |

### L1 单元测试（≤ 3 分钟）

按包分片并行，只跑受影响包（`--affected`）。覆盖率增量门禁：新增代码覆盖率 ≥ 80%，整体不低于基线。

### L2 契约与集成（≤ 5 分钟）

Testcontainers 起 PG、Redis、MinIO，跑仓储与模块间集成。契约快照比对：`contracts` 变更必须与实现同 PR，否则失败。

### L3 构建与签名（≤ 8 分钟）

| 产物 | 构建方式 | 签名 |
| --- | --- | --- |
| 服务镜像 | 多阶段构建，distroless 运行层 | 镜像签名（cosign） |
| 前端静态包 | Vite 构建 + 内容哈希 | 制品哈希入 SBOM |
| Electron 安装包 | electron-builder，三平台 | Windows EV / macOS 公证 |
| 移动端包 | Capacitor + 原生构建 | 应用签名 |
| 插件包 | 打包 + 清单校验 | Ed25519 |

### L4 端到端（≤ 10 分钟）

Playwright 跑 P0 用例，覆盖：登录 → 建会 → 上传 → 开局 → 翻页 → 批注 → 表决 → 闭会 → 导出。真机子集（1 台平板 + 1 台一体机）每晚跑一次全量。

### L5 性能冒烟（≤ 5 分钟）

k6 跑三条关键接口 + 一场 50 终端会议模拟。门禁：P95 劣化 ≤ 10%，错误率 ≤ 0.1%。

### L6 安全（≤ 8 分钟）

| 扫描 | 对象 | 门禁 |
| --- | --- | --- |
| SAST | 源码 | 高危 0 |
| 依赖 | lockfile | 高危 0 |
| 镜像 | 运行层 | 高危 0，中危有豁免单 |
| DAST | Staging 环境 | 高危 0 |
| SBOM | 全部制品 | 必须生成并归档 |

## 23.4 建镜像

```dockerfile
# 构建层
FROM node:22-alpine AS build
WORKDIR /app
COPY pnpm-lock.yaml package.json ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build && pnpm prune --prod

# 运行层：无 shell、无包管理器
FROM gcr.io/distroless/nodejs22-debian12
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
USER 10001
EXPOSE 8080
CMD ["dist/main.js"]
```

三条要求：运行层无 shell（降攻击面）、非 root 用户、镜像内不含源码与密钥。镜像 tag 用 `git-sha` 而非 `latest`，`latest` 只用于本地开发。

## 23.5 制品管理

| 项 | 规定 |
| --- | --- |
| 唯一性 | 一次构建只产出一份制品，全环境复用（构建一次，部署多次） |
| 不可变 | 制品入库后不可覆盖，只可新增 |
| 寻址 | 用内容摘要（sha256）寻址，tag 只是别名 |
| 保留 | 生产制品永久；其他 90 天 |
| 溯源 | 每个制品带 commit、构建号、SBOM、签名 |
| 提升 | 环境提升只改配置，不重新构建 |

「构建一次、部署多次」是保证测试与生产一致的前提。每次环境重新构建的系统，迟早会出现「测试环境好的、生产坏的」。

## 23.6 环境与配置

| 环境 | 部署方式 | 数据 | 审批 |
| --- | --- | --- | --- |
| dev | 每次合入自动 | 构造数据 | 无 |
| test | 每日自动 | 脱敏 | 无 |
| staging | 手动触发 | 脱敏，结构同生产 | 技术负责人 |
| prod | 审批 + 金丝雀 | 真实 | 项目经理 + 运维 |

配置分四级：镜像默认 → 环境变量 → 配置中心 → 数据库动态配置。密钥通过 secret 注入，不入镜像、不入仓库、不进日志。

基础设施即代码：网络策略、存储桶、中间件参数全部用声明式文件管理，变更走 PR。手工改服务器是「不可复现」的源头。

## 23.7 数据库迁移流水线

数据库是流水线里唯一不能「回滚」的东西，因此采用 **expand–contract** 三段式：

| 阶段 | 动作 | 要求 |
| --- | --- | --- |
| expand | 加新列/新表，双写 | 旧代码仍可用 |
| migrate | 回填数据，切换读路径 | 新旧并存，可回退 |
| contract | 删旧列/旧表 | 确认无回退需求后执行 |

每次发布只做其中一段。这样任何一次发布都能用镜像回退来撤销，而不需要「数据库回滚」——后者在实践中几乎总是丢数据。

迁移脚本三条硬规则：可在空库执行、可重复执行（幂等）、有 dry-run 输出。CI 里对迁移做「空库 + 生产快照」双跑。

## 23.8 发布策略

| 策略 | 适用 | 说明 |
| --- | --- | --- |
| 滚动更新 | 无状态服务（api） | 逐批替换，PDB 保底 2 副本 |
| 蓝绿 | 有状态网关 | 新集群起好再切流量 |
| 金丝雀 | 全量发布 | 5% → 30% → 100%，每档观察 30 分钟 |
| 按租户灰度 | 功能上线 | 指定租户先开，出问题只影响他们 |
| Feature flag | 高风险功能 | 代码先上，功能后开，可秒级关闭 |

发布窗口：非会议时段，且未来 2 小时无重要会议。这条不是形式主义——会议中断的代价远高于晚发布几小时。

## 23.9 回滚

| 层 | 手段 | 耗时 |
| --- | --- | --- |
| 应用 | 镜像回退到上一版本 | ≤ 5 分钟 |
| 配置 | 配置中心回退 | ≤ 2 分钟 |
| 功能 | 关闭 feature flag | ≤ 1 分钟 |
| 数据 | 向前兼容设计，不依赖回滚 | — |
| 全站 | 切回备用集群 | ≤ 15 分钟 |

回滚触发条件写成硬指标：错误率 > 1%、同步延迟超阈、任一 P1 缺陷、审计链断裂。达到即执行，不讨论。

每季度做一次「盲回滚」演练：随机选一个历史版本，要求值班人员在不知道原因的情况下完成回退。

## 23.10 审批与留痕

| 发布类型 | 审批人 | 留痕 |
| --- | --- | --- |
| 常规 | 项目经理 | 发布单 + 审批记录 |
| 紧急（hotfix） | 值班负责人 + 事后补审 | 事件单 + 复盘 |
| 数据库结构变更 | 架构师 + DBA | 迁移脚本 + 双跑结果 |
| 安全相关配置 | 安全管理员 | 变更单 + 影响面 |

审批不是走过场：审批人要对「回滚方案是否可行」负责。审批页面上必须展示回滚步骤，而不是只显示「同意/拒绝」。

## 23.11 流水线自身的可靠性

流水线挂了比业务挂了更影响士气。

| 问题 | 对策 |
| --- | --- |
| 偶发失败（flaky） | 自动重试 1 次并标记，连续 3 次进治理清单，两周内必治理 |
| 缓存投毒 | 缓存 key 含 lockfile 哈希，构建机隔离 |
| runner 被污染 | 每次任务用干净容器，不共享工作区 |
| 凭据泄露 | runner 不持有长期凭据，用 OIDC 短期令牌 |
| 流水线变慢 | 设时长预算，超预算即视为缺陷 |

flaky 测试必须治，不能靠重试掩盖。重试只是止血，掩盖的结果是「狼来了」——真失败也被当成偶发。

## 23.12 指标

DORA 四项是行业公认口径，直接沿用：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 部署频率 | 每周生产发布次数 | ≥ 3 次/周 |
| 变更前置时间 | commit 到生产 | ≤ 1 天 |
| 变更失败率 | 导致回滚/热修的发布占比 | ≤ 15% |
| 恢复时间 | 故障到恢复 | ≤ 30 分钟 |

内部补充三项：PR 反馈时长（P50 ≤ 8 分钟）、流水线成功率（≥ 95%）、制品可追溯率（100%）。

## 23.13 常见反模式

| 反模式 | 后果 | 正解 |
| --- | --- | --- |
| 每个环境各自构建 | 测试与生产不一致 | 构建一次，部署多次 |
| `latest` 部署 | 无法确定线上版本 | 按 digest 部署 |
| 手工热修直接改服务器 | 下次发布被覆盖，事故重演 | 热修也走流水线 |
| 数据库迁移与代码同一批 | 无法回滚 | expand–contract 分三次 |
| 用重试掩盖 flaky | 真失败被忽略 | 治理 flaky |
| 审批只看「同意」 | 回滚方案没人验证 | 审批页展示回滚步骤 |
| 流水线无时长预算 | 逐年变慢，无人负责 | 设预算并纳入指标 |
