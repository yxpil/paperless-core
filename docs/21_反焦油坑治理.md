# 21 反焦油坑治理

## 21.0 焦油坑的五个症状

「焦油坑」不是比喻，它有可观察的症状。出现三条以上，项目已经在下沉。

| 症状 | 观察方式 | 典型自欺 |
| --- | --- | --- |
| 改一处要动十处 | 单需求平均改动文件数上升 | 「这些改动都是必要的」 |
| 没人敢改核心 | 核心目录的提交者只剩 1–2 人 | 「他最熟，让他改最快」 |
| 新功能越来越慢 | 同样规模的特性，周期逐季变长 | 「这次需求更复杂」 |
| 缺陷集中在同几个文件 | 缺陷密度分布极度不均 | 「历史遗留，先不动」 |
| 构建与测试越来越慢 | CI 时长逐月上涨 | 「加机器就行」 |

共同点是：**短期每一步都合理，长期整体在恶化**。这正是焦油坑难防的原因——它不由错误决策造成，而由一连串正确的局部最优累积而成。

## 21.1 五个成因

| 成因 | 机制 | 在本项目里的具体形态 |
| --- | --- | --- |
| 边界溶解 | 新功能「顺手」写进已有模块 | 六端渲染内核里混入「PC 才有双屏」的判断 |
| 隐式耦合 | 靠约定而非接口通信 | 业务代码直接读 Redis key 名 |
| 抽象通胀 | 每个客户加一个 if | `if (tenant === 'hosp-A')` 散落各处 |
| 协调开销 | 人多了，沟通路径指数增长 | 六端 + 插件 + 集成，任一端改动牵动全局 |
| 债务复利 | 先欠着，利息随时间增长 | 「先上线，回头重构」——回头永远不来 |

这五个成因里，**边界溶解与抽象通胀**是本项目最大的两个风险，因为客户差异天然要求「定制」，而定制最省事的做法就是加 if。

## 21.2 六道结构性防线

防线的作用不是「提醒大家注意」，而是**让违规在机制上做不出来**。

### 21.2.1 边界防线：依赖方向由 CI 强制

```js
// dependency-cruiser 规则（节选）
{
  name: 'kernel-must-not-depend-on-business',
  from: { path: '^packages/kernel' },
  to: { path: '^(services|apps|plugins)' },
  severity: 'error'
},
{
  name: 'plugins-only-via-sdk',
  from: { path: '^plugins' },
  to: { pathNot: '^(packages/plugin-sdk|packages/contracts)' },
  severity: 'error'
}
```

规则写进 CI，违反即构建失败。这比代码评审里靠人盯有效一个数量级。

### 21.2.2 契约防线：接口先改 contracts，再改实现

任何跨模块调用必须能在 `contracts` 里找到定义。CI 校验两件事：实现里出现的对外方法是否已注册；契约快照是否被未声明地改动。**未登记即失败**，这一条挡住了 80% 的隐式耦合。

### 21.2.3 准入防线：新模块要回答四个问题

| 问题 | 不合格的例子 | 判定 |
| --- | --- | --- |
| 它属于哪个域？ | 「杂项工具」 | 拒绝 |
| 谁拥有它（唯一责任人）？ | 「大家一起维护」 | 拒绝 |
| 它的降级路径是什么？ | 「不会失败」 | 拒绝 |
| 删除它会影响谁？ | 「不知道」 | 拒绝 |

四问答不全，说明这个模块的边界还没想清楚，此时写下去就是焦油。

### 21.2.4 可删除防线：每个功能都要能摘掉

新功能默认用 feature flag 包裹，flag 必须写「删除条件」与「复查日期」。到期未删的 flag 进入债务台账，季度评审强制清理。僵尸 flag 是隐式耦合的温床——半年后没人知道关掉它会发生什么。

### 21.2.5 减法防线：每季度必须删东西

| 季度动作 | 判据 |
| --- | --- |
| 删未使用的接口 | 90 天零调用的公开方法 |
| 删僵尸 flag | 已全量开启超过 60 天 |
| 删重复实现 | 同一能力存在两套（如两套时间格式化） |
| 删过期 ADR 方案 | 已被取代但代码里还留着旧路径 |
| 删无效索引/表 | 无查询命中、无写入的表 |

只加不减的系统，复杂度必然单调上升。减法要排在计划里，否则永远被需求挤掉。

### 21.2.6 规模防线：控制并行工作面

Brooks 定律在这里仍然成立：沟通路径 = n(n-1)/2。8 人团队已是本项目的上限，超过就必须拆成「内核组 / 终端组 / 集成组」，组间只通过契约对话，不通过人对人同步。

## 21.3 十项可测指标

没有数字的治理都是口号。以下指标每月出一次，进架构评审。

| # | 指标 | 健康 | 警戒 | 危险 |
| --- | --- | --- | --- | --- |
| 1 | 单需求平均改动文件数 | ≤ 5 | 6–12 | > 12 |
| 2 | 跨模块依赖条数（新增/月） | ≤ 3 | 4–8 | > 8 |
| 3 | 内核新增公开 API（/月） | ≤ 2 | 3–5 | > 5 |
| 4 | 核心目录提交者数量 | ≥ 3 | 2 | 1 |
| 5 | 圈复杂度 > 15 的函数占比 | < 3% | 3–8% | > 8% |
| 6 | 重复代码率 | < 3% | 3–8% | > 8% |
| 7 | CI 时长 | < 12 分钟 | 12–25 分钟 | > 25 分钟 |
| 8 | 缺陷密度（每千行） | < 1.5 | 1.5–4 | > 4 |
| 9 | 债务条目平均年龄 | < 60 天 | 60–180 天 | > 180 天 |
| 10 | 僵尸 flag 数量 | 0 | 1–5 | > 5 |

第 3 项特别值得盯：**内核 API 只增不减，就是内核在变成第二个业务层**。内核每加一个对外方法，都要问「这属于能力还是属于插件」。

## 21.4 治理仪式

| 频率 | 活动 | 时长 | 产出 |
| --- | --- | --- | --- |
| 每周 | 架构门诊 | 60 分钟 | 本周新增依赖与例外审批 |
| 每月 | 指标复盘 | 30 分钟 | 十项指标的走势与处置 |
| 每季 | 减法日 | 1 天 | 删除清单与执行结果 |
| 每季 | 债务预算结算 | 30 分钟 | 用掉多少、还剩多少 |
| 每半年 | 架构复审 | 2 小时 | ADR 是否仍成立，是否需要取代 |

仪式必须短、有产出、可追踪。超过 2 小时的评审会没人愿意开第二次。

## 21.5 十条早期预警

1. 有人开始在 PR 里写「临时方案，后续重构」。
2. 同一个概念出现三个名字（会议/房间/会话混用）。
3. 新人上手需要「找某个人问」才能跑通。
4. 单元测试开始大量 mock 内部实现而非外部依赖。
5. 同一个 bug 在两端各修一次。
6. 出现「不要动那个文件」的口头约定。
7. 性能问题靠加机器解决，而不是定位。
8. 需求评审开始讨论「这次能不能不改内核」。
9. 发布回滚次数上升，且原因都是「没想到会影响 X」。
10. 文档与代码对不上，且没人愿意更新文档。

第 9 条最危险：它说明系统内部已经存在没人掌握的隐式耦合。

## 21.6 八条红线

| # | 红线 | 检查方法 |
| --- | --- | --- |
| 1 | 内核不得引用业务模块 | dependency-cruiser |
| 2 | 不得出现第二套状态管理 | 代码扫描（多个 store 库） |
| 3 | 不得直连他人数据库 | 连接串集中管理 + 扫描 |
| 4 | 不得绕过能力接口访问数据 | 仓储层之外的 SQL 扫描 |
| 5 | 六端不得各自实现业务判断 | 相同逻辑出现在多个 app 目录 |
| 6 | 不得保留无降级路径的关键功能 | 准入四问 |
| 7 | 不得在业务代码里出现租户名/客户名 | 关键字扫描 |
| 8 | 不得让安全层被覆盖 | 渲染层单测断言 z 序 |

红线一旦触碰，不是「下次注意」，而是**当次不合入**。红线如果可以被商量，它就不叫红线。

## 21.7 技术债台账与利息

债务不是道德问题，是财务问题。平台用台账管理，每条债务记五个字段：

| 字段 | 示例 |
| --- | --- |
| 描述 | 会议列表分页用 offset，深翻页慢 |
| 利息 | 每万条数据 +80 ms |
| 触发条件 | 单租户会议数 > 5 万 |
| 偿还成本 | 3 人日 |
| 复查日期 | 2027-03-01 |

利息必须可估。估不出利息的债务，通常不是债务，是「我们不打算做」。

债务预算：每季度固定 15%–20% 产能用于偿还，不许挪用。挪一次就会有第二次。

## 21.8 范围侧的防膨胀

技术焦油坑往往由需求焦油坑引起。本项目从第一轮到第三轮，需求条目增长了数倍，这是明确的信号。

| 机制 | 做法 |
| --- | --- |
| 范围基线 | 第 00 章的核对表即基线，新增必须标注「替换哪项 / 推迟到哪期」 |
| 变更门 | 影响 > 5 人日或触及内核的需求，走变更评审 |
| 分期承诺 | 对客户只承诺当期，后续入库不承诺时间 |
| 需求折旧 | 每季度清理一次「提了但没人再用」的需求 |

一句话：**没有范围基线的项目，一定会变成焦油坑**，因为它连「做完」都无法定义。

## 21.9 该重构还是该冻结

| 信号 | 判断 | 动作 |
| --- | --- | --- |
| 局部混乱，边界清晰 | 重构 | 小步重构，每次 ≤ 3 人日 |
| 边界本身错了 | 重写该模块 | 先写新模块并行跑，再切换 |
| 内核边界错了 | 冻结 + 分区 | 停止加功能，先切分内核 |
| 只是「看着不顺眼」 | 不动 | 审美不是重构理由 |

重构的安全网是测试。没有测试的重构叫赌博，不叫重构。

## 21.10 30 天体检清单

接手一个已经跑了一段时间的系统，按这十项做一次体检，比读一周代码有效。

| # | 检查 | 判据 |
| --- | --- | --- |
| 1 | 画出模块依赖图 | 是否存在环 |
| 2 | 找出被依赖最多的 5 个模块 | 是否都是「工具」类 |
| 3 | 统计核心目录提交者 | 是否 ≥ 3 人 |
| 4 | 跑一次全量测试 | 时长与失败率 |
| 5 | 找 3 个最近的需求 | 改动文件数与是否触及内核 |
| 6 | 列出所有 feature flag | 有多少僵尸 |
| 7 | 抽查 5 个接口 | 是否都在 contracts 登记 |
| 8 | 查日志规范 | 是否能按 traceId 串起来 |
| 9 | 查一次故障复盘 | 根因是「没想到」还是「已知未修」 |
| 10 | 问三个人「这个系统最难改的地方」 | 答案是否一致 |

答案不一致，说明认知没有共享，这就是焦油坑的起点。
