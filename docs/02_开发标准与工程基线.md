# 02 开发标准与工程基线

## 2.1 技术栈基线

| 层 | 选型 | 版本 | 约束理由 |
| --- | --- | --- | --- |
| 运行时 | Node.js LTS | 22.x | 单一运行时贯穿服务端与终端外壳，降低人力成本 |
| 语言 | TypeScript | 5.6+ | `strict` 全开，禁用 `any` 逃逸 |
| 服务端框架 | NestJS | 11 | 模块边界清晰，插件可复用其 DI 容器 |
| HTTP | Fastify | 5 | 吞吐高于 Express，原生 schema 校验 |
| 数据库 | PostgreSQL | 16 | JSONB + 逻辑复制，适合元数据与事件 |
| 缓存/定序 | Redis | 7.2 | Lua 原子定序、会话、限流 |
| 对象存储 | MinIO（S3 兼容） | 最新稳定 | 私有化部署，可换任意 S3 |
| 消息 | NATS JetStream | 2.10 | 轻量、可持久、易嵌入 |
| 设备通道 | EMQX | 5.8 | MQTT over TLS，老设备友好 |
| 检索 | OpenSearch | 2.15 | 可插拔分析器，中文分词可选 |
| 前端 | React + Vite | 18.3 / 5 | 六端共享一套渲染内核 |
| 终端外壳 | Electron | 28 | 双屏、系统水印、本地文件能力 |
| 移动外壳 | Capacitor | 6 | 复用 Web 代码，保留原生笔迹 |
| 包管理 | pnpm + Turborepo | 9 / 2 | 单仓多包，增量构建 |

技术栈锁定三年不变。任何替换必须写 ADR 并在第 03 章备案，不允许在插件里私自引入第二套框架。

## 2.2 仓库结构

```
paperless/
├─ packages/
│  ├─ kernel/            # 内核：身份、权限、会话、rev、审计钩子
│  ├─ contracts/         # 全部 DTO / 事件 / 错误码，唯一真源
│  ├─ plugin-sdk/        # 插件 SDK：manifest 校验、能力调用、生命周期
│  ├─ render-core/       # 六端共享渲染内核（文档、页帧、批注）
│  ├─ design-tokens/     # 设计令牌，产出 CSS 变量与平台映射
│  └─ test-kit/          # 契约回放、假时钟、测试数据工厂
├─ services/
│  ├─ api/               # 业务接口（内核 + 内置插件装配）
│  ├─ ws-gateway/        # 长连接、鉴权、事件路由
│  ├─ sync-worker/       # 房间状态推进与广播
│  ├─ doc-worker/        # 转帧、排版、导出
│  ├─ media-worker/      # 录播、转码、ASR 编排
│  ├─ search/            # 联邦检索与索引写入
│  ├─ bridge/            # 对外 API 桥接与协议转换
│  └─ audit-relay/       # 审计批量签名与外推
├─ apps/
│  ├─ desktop/           # Electron 主进程 + 渲染
│  ├─ tablet/            # Capacitor 壳
│  ├─ web/               # 网页端（含 TV 只读模式）
│  ├─ board/             # 白板端
│  └─ kiosk/             # 一体机端
├─ plugins/              # 官方插件源码（与第三方插件同构）
├─ infra/                # compose、k8s、迁移、密钥模板
└─ docs/                 # 本套文档
```

依赖规则：`kernel` 不依赖任何 `service`；`contracts` 不依赖任何运行时包；`plugins` 只能依赖 `plugin-sdk` 与 `contracts`。CI 用 `dependency-cruiser` 强制，出现反向依赖直接失败。

## 2.3 编码规范

- 命名：文件 `kebab-case`，类型 `PascalCase`，函数与变量 `camelCase`，常量 `UPPER_SNAKE`，事件类型 `域.动作` 形如 `room.material.publish`。
- 错误：一律用 `AppError`，带 `code`（第 07 章错误码表）、`message`、`traceId`、`retryable`。禁止抛裸字符串。
- 异步：禁止裸 `Promise` 悬挂，所有外部调用必须带超时（默认 3 秒）与取消信号。
- 事务：跨聚合的写操作必须走「领域事件 + 最终一致」，不允许跨模块长事务。
- 时间：服务端统一 UTC 存储，输出按租户时区渲染；时间字段命名以 `At` 结尾。
- 日志：结构化 JSON，字段固定为 `ts、level、service、traceId、tenantId、actorId、event、durationMs、err`。日志中禁止出现材料正文与个人证件号。

## 2.4 Git 与评审

| 项 | 规则 |
| --- | --- |
| 分支 | `main`（可发布）、`release/*`（冻结）、`feat/*`、`fix/*`、`hotfix/*` |
| 提交 | Conventional Commits，`feat(collab): 支持页帧批注批量撤销` |
| 粒度 | 一次提交只做一件事；跨模块改动必须拆 |
| 评审 | 至少 1 人通过；涉及内核、权限、加密、迁移必须 2 人 |
| 合并 | squash 合并到 `main`，保留 PR 标题作为提交信息 |
| 禁入 | 密钥、证书、真实材料、生产数据；由 secret 扫描拦截 |

## 2.5 质量门

| 门禁 | 阈值 | 失败处理 |
| --- | --- | --- |
| 类型检查 | 0 error | 阻断合并 |
| 单元测试 | 内核与 contracts 覆盖率 ≥ 80%，其他 ≥ 60% | 阻断 |
| 集成测试 | 关键路径 100% 覆盖 | 阻断 |
| 契约测试 | 与 `contracts` 快照一致 | 阻断 |
| 依赖漏洞 | 高危 0，中危有豁免单 | 阻断 |
| 包体积 | 网页首屏 JS ≤ 300 KB（gzip） | 警告 |
| 性能回归 | 关键接口 P95 劣化 ≤ 10% | 阻断发布 |

质量门只保证「本次不更糟」，不保证「长期不变坏」。防止系统整体滑向焦油坑的机制（依赖方向强制、准入四问、减法日、十项指标与红线）见第 21 章。

## 2.6 Electron 构建

### 2.6.1 进程职责

主进程只做四件事：窗口与双屏管理、系统级能力（水印、防截屏、文件对话、托盘）、更新、IPC 网关。渲染进程不直接访问文件系统与网络，全部经 IPC 走主进程的能力白名单。预加载脚本暴露的 API 数量必须收敛，每个方法单独登记，不允许 `ipcRenderer` 直通。

### 2.6.2 构建产物

| 平台 | 目标 | 说明 |
| --- | --- | --- |
| Windows | NSIS 安装包 + 便携版 | 支持静默安装与域策略下发 |
| macOS | dmg + zip（universal） | 需公证 |
| Linux | AppImage + deb | 麒麟/统信单独出包 |
| 国产化 | ARM64 / 龙芯（LoongArch） | 需单独验证 Electron 运行时可用性 |

### 2.6.3 签名与更新

- Windows 使用 EV 代码签名证书，签名后校验 SmartScreen 信誉；macOS 走 `notarytool` 公证。
- 更新走私有源：`electron-updater` 指向内网更新服务，更新包用 Ed25519 签名，客户端验签后才安装。
- 更新策略为「灰度环」：内测环 5%、稳定环 30%、全量；任一环失败率超过 2% 自动停止推进。
- 离线场景提供整包升级（U 盘分发），升级包同样验签。

```json
{
  "appId": "com.example.paperless",
  "productName": "PaperlessCore",
  "directories": { "output": "dist" },
  "win": {
    "target": [{ "target": "nsis", "arch": ["x64", "arm64"] }],
    "signingHashAlgorithms": ["sha256"],
    "sign": "./scripts/sign-win.js"
  },
  "mac": { "target": ["dmg", "zip"], "hardenedRuntime": true },
  "linux": { "target": ["AppImage", "deb"], "category": "Office" },
  "publish": [{ "provider": "generic", "url": "https://update.example.com/paperless" }]
}
```

### 2.6.4 更新与滚动的硬约束

内核版本与终端版本必须做兼容矩阵：终端声明自己支持的协议版本区间，服务端在下发能力时取交集。禁止「服务端先升级、老终端直接不可用」的发布方式，正确做法是服务端同时支持新旧协议至少两个版本周期。

## 2.7 插件开发规范

插件是被内核装载的功能单元，必须满足五条：

1. 有 `manifest.json`，声明 `id、version、type、capabilities、permissions、entry、contractVersion`。
2. 只通过 SDK 访问内核，禁止直接连数据库、读环境变量、开监听端口。
3. 所有对外暴露的接口在 `contracts` 中登记，未登记不可调用。
4. 有卸载清理逻辑，卸载后不留残留表与残留文件（残留表以命名空间前缀隔离）。
5. 有健康检查与降级路径，插件崩溃不得导致会议中断。

插件类型见第 04 章，此处只锁定工程约束。

## 2.8 文档与 ADR

- 每个跨模块决策写 ADR，模板为「背景 / 选项 / 决定 / 代价 / 复审时间」。
- ADR 编号连续，存于 `docs/adr/`，一旦接受不改写，只能新增「取代 ADR-xxx」。
- 接口变更先改 `contracts`，再改实现，最后改文档；顺序颠倒视为违规。

## 2.9 依赖与供应链

- 只用 pnpm 锁定的版本，禁止 `latest`。
- 新增运行时依赖需说明：许可证、维护活跃度、体积、替代方案。GPL 系依赖禁入。
- 每月执行一次 `pnpm audit` 与 SBOM 生成，SBOM 随版本归档。
- 构建环境与运行环境分离，构建机不持有生产密钥。

## 2.10 发布基线

| 项 | 规定 |
| --- | --- |
| 版本号 | 语义化，`主.次.修订`；内核与终端各自独立版本 |
| 发布单 | 含变更清单、影响面、回滚方案、验证清单 |
| 窗口 | 非会议时段，提前 3 个工作日通知 |
| 灰度 | 5% → 30% → 100%，每档观察不少于 2 小时 |
| 回滚 | 镜像回退为主，数据库变更向前兼容 |

发布的具体流水线阶段、时长预算、制品签名、金丝雀推进与回滚演练，见第 23 章《CI/CD 流水线》。
