# 22 进度控制与考核

## 22.0 为什么进度总是不准

进度失控很少是「有人偷懒」，多数是三个结构性原因：

| 原因 | 机制 | 表现 |
| --- | --- | --- |
| 估算乐观 | 人按「一切顺利」估，不按历史均值估 | 每次都说「这次差不多」 |
| 学生综合征 | 任务总在截止前完成，提前做完也不上报 | 前期进度 60% 卡很久，最后一天冲到 100% |
| 完成度自评 | 「90% 完成」可以维持三个月 | 进度表好看，交付物没有 |

结论：**进度不能靠自评，只能靠可验证产出与外部观察**。本章的所有机制都围绕这一条。

## 22.1 三条基准

| 基准 | 内容 | 变更方式 |
| --- | --- | --- |
| 范围基准 | 第 00 章核对表 + 各章功能清单 | 变更单，注明替换/推迟 |
| 时间基准 | 里程碑与迭代计划 | 里程碑变更需管理层批准 |
| 质量基准 | 第 02 章质量门 + 第 21 章红线 | 不可下调 |

三条基准必须同时冻结。只冻时间不冻范围，必然靠降质量来填坑——这是最常见的技术债来源。

## 22.2 工作分解

按交付域分解，不按「人」分解。按人分解会导致「谁有空谁做」，边界随之溶解。

| 一级 | 二级（示例） | 验收物 |
| --- | --- | --- |
| 内核 | 身份与权限 / 会话与 rev / 对象存储 / 审计钩子 | 接口契约 + 集成测试 |
| 会议 | 状态机 / 议程 / 材料 / 表决 / 纪要 | 端到端用例通过 |
| 终端 | 渲染内核 / PC 壳 / 平板壳 / 白板 / 一体机 / 网页 TV | 六端截图 + 性能报告 |
| 协作 | 批注 / 白板协同 / 表格协作 / 版本协商 | 并发场景测试 |
| 检索 | 采集 / 索引 / 联邦查询 / 溯源 | 检索准确率报告 |
| 安全 | 加密 / KMS / 审计链 / 危险感知 | 等保预评 + 渗透报告 |
| 集成 | 桥接网关 / 财务 / 传统系统 / 插件体系 | 联调记录 |
| 交付 | 部署 / 模板包 / 培训 / 验收 | 验收报告 |

每个二级工作包必须有：唯一责任人、交付物、完成定义（DoD）、估算人日。缺任一项不能进计划。

## 22.3 估算与缓冲

| 方法 | 用法 | 注意 |
| --- | --- | --- |
| 三点估算 | `(乐观 + 4×最可能 + 悲观) / 6` | 悲观值必须来自历史，不是拍脑袋 |
| 历史类比 | 用同类模块的实际人日 | 需要有人日台账，否则无从类比 |
| 功能点 | 只用于对外报价，不用于内部排期 | 换算系数易失真 |

缓冲分两级，不要混在一起：

| 缓冲 | 归属 | 比例 | 谁能动 |
| --- | --- | --- | --- |
| 任务缓冲 | 每个工作包内 | 15% | 责任人 |
| 项目缓冲 | 里程碑末 | 20% | 项目经理 |

关键原则：**缓冲集中在里程碑，不撒在每个任务里**。撒在任务里会被逐个「用掉」，且没人承认用了。

## 22.4 里程碑门禁

里程碑不是「时间点」，是**门禁**：不满足条件不得进入下一阶段。

| 门 | 进入条件 | 签字人 |
| --- | --- | --- |
| G0 立项 | 范围基线、预算、编制确认 | 项目发起人 |
| G1 设计冻结 | 架构与契约评审通过，ADR 归档 | 架构师 + 技术负责人 |
| G2 功能完成 | P0 用例 100% 通过，无 P1 缺陷 | 测试负责人 |
| G3 可交付 | 等保预评通过，部署演练成功 | 安全 + 运维 |
| G4 验收 | 客户验收清单全通过 | 客户 + 项目经理 |
| G5 结项 | 复盘报告、债务台账移交 | 管理层 |

门禁的价值在于**拒绝「差不多可以了」**。没有签字人，就没有责任主体。

## 22.5 进度度量

### 22.5.1 挣值三值

| 量 | 定义 | 本项目的取法 |
| --- | --- | --- |
| PV（计划值） | 按计划应完成的工作价值 | 工作包人日累计 |
| EV（挣值） | 实际完成的工作价值 | **只算通过 DoD 的工作包** |
| AC（实际成本） | 实际投入 | 人日台账 |

| 指标 | 公式 | 判读 |
| --- | --- | --- |
| SPI | EV / PV | < 0.9 进度落后 |
| CPI | EV / AC | < 0.9 成本超支 |
| ETC | (BAC − EV) / CPI | 完工尚需估算 |

关键在 EV 的取法：**「写完了」不算，必须 DoD 通过**。DoD 至少包含：代码合入、测试通过、文档更新、契约登记。这一条能挡掉绝大部分「90% 完成」的幻觉。

### 22.5.2 三个辅助视图

| 视图 | 用途 | 频率 |
| --- | --- | --- |
| 燃尽图 | 剩余工作包数 vs 时间 | 每日 |
| 累积流图 | 各状态（待办/开发/评审/测试/完成）的堆积 | 每周 |
| 缺陷趋势 | 新增 vs 关闭 | 每周 |

累积流图比燃尽图更有用：它直接暴露瓶颈在哪个环节（评审堆积说明评审人力不足，测试堆积说明质量前移没做好）。

### 22.5.3 完成百分比的正确用法

只允许三种状态：未开始、进行中、已完成（DoD 通过）。禁止「完成 70%」。

如果一定要粒度，用「工作包内子项计数」：例如 8 个接口完成 5 个，即 5/8。可数、可核、不可美化。

## 22.6 偏差处置

| 信号 | 判定 | 动作 |
| --- | --- | --- |
| SPI 在 0.9–1.0 | 黄灯 | 项目经理调整任务顺序，不动范围 |
| SPI < 0.9 连续两周 | 红灯 | 上报，进入偏差处置流程 |
| 关键路径任务延迟 > 3 天 | 红灯 | 立即评估替代路径 |
| 缺陷逃逸率 > 5% | 红灯 | 暂停新功能，先稳质量 |

处置手段有优先级，**顺序不能颠倒**：

| 顺序 | 手段 | 代价 | 风险 |
| --- | --- | --- | --- |
| 1 | 减范围（推迟 P1/P2） | 客户不满 | 可控 |
| 2 | 调顺序（并行非关键路径） | 协调成本 | 中 |
| 3 | 快速跟进（把串行改并行） | 返工风险 | 高 |
| 4 | 赶工（加班） | 质量下降、士气 | 高 |
| 5 | 加人 | 沟通成本、上手期 | **最高** |

加人排最后，因为 Brooks 定律：向已经延迟的项目加人，只会让它更延迟。新人上手期通常 2–4 周，且会占用老人的时间。

## 22.7 汇报节奏

| 频率 | 形式 | 时长 | 内容 |
| --- | --- | --- | --- |
| 每日 | 站会 | 15 分钟 | 昨天完成、今天计划、阻塞 |
| 每周 | 周报 | 1 页 | SPI/CPI、里程碑状态、Top3 风险、需要决策项 |
| 每月 | 月度复盘 | 60 分钟 | 指标走势、偏差处置效果、下月预测 |
| 每里程碑 | 门禁评审 | 90 分钟 | 交付物演示 + 证据清单 + 签字 |

周报固定五个字段，不允许写成散文：

```
里程碑: G2 功能完成  状态: 黄   SPI 0.94
本周完成: 表决模块闭环（DoD 通过）
下周计划: 纪要签审、分组房间
Top风险: 转帧服务在大文件上超时（影响 G2）
需决策: 是否将 PDF 表单填写推迟到 P1
```

「需决策」一栏空着，说明要么没风险，要么不敢报。后者更危险。

## 22.8 考核体系

考核最容易做错的地方是**考过程不考结果**，或者**考个人不考系统**。

### 22.8.1 三层结构

| 层 | 考什么 | 权重示例 |
| --- | --- | --- |
| 项目层 | 里程碑达成、验收一次通过、预算 | 40% |
| 团队层 | 交付质量、缺陷逃逸、协作效率 | 35% |
| 个人层 | 承诺兑现、评审质量、知识贡献 | 25% |

项目层权重最高，是为了避免「个人指标漂亮、项目延期」。

### 22.8.2 指标表

| 层 | 指标 | 口径 | 目标 |
| --- | --- | --- | --- |
| 项目 | 里程碑按期率 | 按门禁签字时间 | ≥ 85% |
| 项目 | 验收一次通过率 | 首次验收即通过 | ≥ 80% |
| 项目 | 预算偏差 | (AC − BAC)/BAC | ≤ 10% |
| 团队 | 缺陷逃逸率 | 上线后发现的/总缺陷 | ≤ 5% |
| 团队 | CI 健康度 | 主干绿时长占比 | ≥ 95% |
| 团队 | 需求交付周期 | 从进入到 DoD | ≤ 15 个工作日 |
| 个人 | 承诺兑现率 | 按期完成的工作包占比 | ≥ 90% |
| 个人 | 评审有效性 | 评审中发现的问题数/被评审变更 | 有记录即可 |
| 个人 | 缺陷引入 | 由其变更导致的缺陷 | 趋势下降 |
| 个人 | 知识贡献 | 文档、ADR、分享 | 每人每季 ≥ 1 |

### 22.8.3 禁止的指标

| 禁止 | 原因 |
| --- | --- |
| 代码行数 | 鼓励写冗余代码 |
| 提交次数 | 鼓励碎片提交 |
| 工时填报率 | 鼓励填表而非干活 |
| 加班时长 | 鼓励低效 |
| 「工作量饱和」主观评分 | 无法校准 |

一个判断标准：**这个指标能不能通过降低系统质量来改善？** 能，就不要用。

### 22.8.4 评级与分布

不建议强制分布（如 20% 优秀）。强制分布在 8 人团队里会制造内耗，且与「协作」目标冲突。

建议做法：先定标准（达到/超出/未达），再按标准评级；优秀比例不设上限，但需上一级复核。同时设「项目奖金池」，与项目层指标挂钩，团队共享——这比个人排名更能促成协作。

## 22.9 奖惩与挂钩

| 情形 | 处理 |
| --- | --- |
| 里程碑提前且质量达标 | 奖金池上浮，团队共享 |
| 里程碑延期由可控原因造成 | 扣减当期奖金，项目经理承担主要责任 |
| 延期由客户变更造成 | 走变更单，不计入考核 |
| 出现 P1 缺陷或安全事件 | 当期考核不得评优 |
| 主动暴露风险并化解 | 正向记录，纳入评优 |

最后一条很重要：**报风险要被奖励，而不是被追责**。否则所有人都会把风险藏到爆炸那天。

## 22.10 外包与供应商考核

| 指标 | 口径 |
| --- | --- |
| 交付准时率 | 按合同节点 |
| 一次验收通过率 | 首次提交即通过 |
| 缺陷密度 | 每千行或每功能点 |
| 响应时效 | 问题提出到首次响应 |
| 知识转移 | 文档与培训完成度 |

外包考核必须与「知识转移」挂钩，否则项目结束后没人接得住。

## 22.11 复盘

| 类型 | 时点 | 输出 |
| --- | --- | --- |
| 迭代复盘 | 每两周 | 三条改进项，下期验证 |
| 里程碑复盘 | 每门禁后 | 偏差根因、流程修正 |
| 项目终验复盘 | 结项 | 复盘报告、债务台账移交 |

复盘的三条纪律：只谈事实不谈人；每条改进必须有责任人与验证方式；上次的改进项必须逐条回顾是否生效。

不做第三条，复盘就会变成「每次都提同样的问题」。

## 22.12 常见失真与对策

| 失真 | 表现 | 对策 |
| --- | --- | --- |
| 进度虚高 | 大量任务「进行中」不动 | 限制 WIP，超限不许开新任务 |
| 风险瞒报 | 周报「一切正常」 | 风险上报正向激励 + 匿名通道 |
| 指标游戏 | 拆分任务刷完成数 | 按工作包计，不按子任务计 |
| 加班常态化 | 计划本身就不可能完成 | 计划必须包含缓冲，加班不计入产能 |
| 考核政治化 | 评分靠印象 | 指标先行、口径公开、可申诉 |

最后一条决定考核体系能否活过第二年。口径不公开的考核，一定会退化成「领导印象分」。
