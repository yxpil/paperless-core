# 26 需求工程与变更控制

## 26.1 需求从哪来

| 来源 | 特征 | 处理方式 |
| --- | --- | --- |
| 客户业务方 | 场景真实，但常以「功能」表述 | 还原成问题，再定方案 |
| 合规与安全 | 硬约束，不可谈 | 直接进基线，标红线 |
| 销售/售前 | 承诺风险高 | 一律入库评审，不当场承诺 |
| 交付/实施 | 现场痛点 | 高频且可复现的优先 |
| 内部技术债 | 不产生客户价值 | 走技术债预算，不占需求产能 |

最危险的是「销售当场答应的需求」。它的特点是：没有验收标准、没有优先级、没有截止时间，最后变成所有人都记得但没人负责的悬案。

## 26.2 需求池与优先级

所有需求进一个池子，统一编号，统一评估。禁止「微信里说一句就开工」。

| 方法 | 用法 | 适用 |
| --- | --- | --- |
| MoSCoW | 必须/应该/可以/不做 | 单客户版本规划 |
| RICE | 触达 × 影响 × 信心 / 投入 | 多客户横向比较 |
| 价值-成本-风险 | 三维打分 | 大需求取舍 |

优先级的三个硬约束：合规项永远最高；影响会议能否进行的优先于体验优化；跨客户的共性需求优先于单客户定制（定制走插件）。

## 26.3 需求评审

每个需求过三问，答不全就打回：

1. **解决谁的什么问题？** 说不出具体角色和场景，就是伪需求。
2. **不做会怎样？** 答案是「也能凑合」，就该进「可以」而不是「必须」。
3. **怎么判验收？** 说不出可验证标准，就无法验收，也无法计挣值。

评审输出四件：需求编号、优先级、验收标准、影响面（是否触及内核/契约/数据库）。

## 26.4 需求文档的最小结构

| 要素 | 内容 | 缺失后果 |
| --- | --- | --- |
| 编号 | FR-域-序号 | 无法追踪 |
| 描述 | 一句话说清能力 | 各自理解不同 |
| 角色 | 谁使用 | 权限设计缺失 |
| 前置条件 | 依赖的状态/权限/数据 | 边界不清 |
| 主流程 | 正常路径 | — |
| 异常流程 | 失败/降级/越权 | 上线后全是异常 |
| 验收标准 | 可测判据 | 无法验收 |
| 优先级 | P0/P1/P2 | 排期靠吵 |

异常流程是最常被省略的一段，也是缺陷最集中的地方。一个需求如果只写了主流程，它就没写完。

## 26.5 变更控制

变更不可怕，可怕的是无声变更。

| 变更类型 | 判定 | 流程 |
| --- | --- | --- |
| 澄清 | 不改变范围与验收 | 记录即可 |
| 小变更 | 影响 ≤ 5 人日，不动内核 | 项目经理批准 |
| 大变更 | 影响 > 5 人日或触及内核/契约/库结构 | 变更评审（CCB） |
| 紧急变更 | 生产事故导致 | 先执行，24 小时内补审 |

CCB 的输入必须包含四样：变更内容、影响面、对进度的影响、替换或推迟的方案。**没有「替换/推迟」这一栏的变更申请，一律不批**——否则范围只会单向增长。

变更记录进变更台账，与需求编号关联。半年后回溯「为什么这个版本延期」，答案应该能在台账里找到。

## 26.6 追踪矩阵

一条需求要能顺着链走到底：

```
FR-会议-012
  → 设计：05 §5.3、16 §16.3
  → 契约：contracts/meeting/start.json
  → 代码：services/api/src/meeting/start.ts
  → 用例：TC-MTG-0341
  → 验收：验收清单 3.2
```

矩阵不全，说明有环节在「凭记忆」推进。CI 可以自动校验：每个 FR 是否有对应用例；每个契约变更是否有关联需求。

## 26.7 冻结与折旧

| 动作 | 时点 | 规则 |
| --- | --- | --- |
| 范围冻结 | 每个迭代开始 | 迭代内不接新需求 |
| 版本冻结 | 发布前 2 周 | 只修 P1/P2 |
| 需求折旧 | 每季度 | 清理「提了但没人再用」的需求 |

折旧这条很少人做，但它能防止需求池变成垃圾场：池子里躺着一千条需求，没人知道哪些还真要做。

## 26.8 与干系人对齐

| 对象 | 对齐内容 | 频率 |
| --- | --- | --- |
| 客户业务方 | 验收标准、上线时间 | 每迭代 |
| 客户 IT/安全 | 网络、证书、审计对接 | 里程碑 |
| 销售 | 承诺边界（能做什么、不能做什么） | 需求入库时 |
| 交付 | 配置项与模板 | 每次变更 |

对销售最重要的一句话是「不承诺时间，只承诺入库」。这句话能省掉后面 80% 的扯皮。

## 26.9 五种典型病态需求

| 病态 | 表现 | 处理 |
| --- | --- | --- |
| 伪需求 | 「别人都有，我们也要」 | 追问场景，说不出就拒 |
| 镀金 | 「顺便再加个动画」 | 进「可以」级，不占当期 |
| 口头需求 | 「上次开会说过的」 | 无编号不受理 |
| 无限迭代 | 「再改一版看看」 | 明确「最多两版」写进约定 |
| 转嫁风险 | 「先做，出问题再说」 | 拒绝，要求先定验收 |

第五条尤其要警惕：把不确定性转嫁给研发的需求，最后一定以延期和质量问题收场。
