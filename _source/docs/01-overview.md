# 1 文档目的与适用范围

## 1.1 编写目的

本套文档面向一套以 Node.js 为服务端主体、覆盖 PC、平板、一体机、白板、网页、TV 六类终端的无纸化会议系统（工程代号 PaperlessCore，以下简称“本系统”），给出从概念定义、需求、概要设计、详细设计、接口协议、UI 标准、老设备接入，到安全合规、部署运维与测试验收的完整技术基线。

编写目的有三项。第一，把“无纸化”从一个营销概念还原为可交付、可验收的工程对象，明确它做什么、不做什么、以什么指标衡量。第二，为六端与服务器端的并行开发提供唯一事实来源，避免各端自行定义消息格式、状态语义和视觉规范，导致联调阶段返工。第三，把企业级开发标准固化为可执行的规则与阈值，使质量不依赖个人经验。

## 1.2 适用范围

本套文档适用于本系统的立项论证、招投标技术响应、概要设计与详细设计评审、编码实现、集成测试、等保测评整改、部署实施与运维移交。不适用于硬件结构与外观工业设计、会议室声学与灯光工程、涉密网络的分级保护测评实施细节，上述内容由对应专业单位另行出具文件。

## 1.3 读者对象

产品经理与售前技术人员阅读第 1、2 分册，用于界定范围与编写方案；架构师与后端工程师阅读第 3、4、7 分册；前端与终端工程师阅读第 5、6 分册；测试与实施人员阅读第 2、8 分册；运维与安全管理人员阅读第 7、8 分册；项目管理层阅读第 1 分册第 6、8 章。

## 1.4 文档约定

文档编号采用 PLS-DOC-NN 形式，本套共 8 册。正文层级统一使用阿拉伯数字小数编号（1、1.1、1.1.1），不使用中文公文层级，以保证技术条款可被逐条引用。所有需求条目使用 FR/NFR 前缀编号，所有架构决策使用 ADR 编号，所有接口使用资源名加动作名，所有数据库表使用小写下划线命名。

# 2 什么是无纸化

## 2.1 概念界定

无纸化不是“把纸换成屏幕”，而是把会议的信息流从“纸质载体的物理流转”改造成“数字载体的权限流转”。判断一套系统是否真正实现无纸化，不看它是否配了升降屏或平板，而看三条信息流是否闭环：

- 材料流：材料从起草、审签、分发、批注、版本替换到归档，全程不产生纸质副本，且每一次分发都可追溯到具体接收人。
- 过程流：签到、议程推进、同屏、表决、决议、纪要形成过程数据，过程数据可被系统自动采集而不是人工回填。
- 决策流：会议形成的决议、任务、责任人、时限进入可跟踪的任务体系，而不是停留在纸面纪要上。

据此，本系统把“无纸化”定义为：以统一身份与权限为基础，以材料集中管控为核心，以多终端实时同步为手段，以过程留痕与归档为闭环的会议信息基础设施。

## 2.2 与传统会议系统的差别

传统会议系统（会议扩声、讨论型会议、视频会议）解决的是“听得见、看得见”，本系统解决的是“看得对、改得动、留得住”。差别集中在四个方面。

表 1 传统会议系统与无纸化系统的对比

| 对比维度 | 传统会议系统 | 本系统（PaperlessCore） |
| 信息载体 | 纸质材料 + 投影幕布 | 集中托管的电子材料 + 多端页帧同步 |
| 材料版本 | 会前打印，会中改稿靠口头与手写 | 版本号受控，替换即时下发，旧版自动作废 |
| 权限控制 | 靠会场秩序与人工发放 | 按人、按议程、按时间窗授权，离会即回收 |
| 过程记录 | 人工记录，事后整理 | 事件级留痕，纪要自动生成初稿 |
| 终端要求 | 投影 + 话筒 + 人工 | 六端能力协商，老设备经网关降级接入 |
| 数据安全 | 纸质材料易带出、难追溯 | 水印、防截屏、审计、离会销毁 |

## 2.3 业务价值与可量化指标

无纸化的价值必须可量化，否则无法通过验收。本系统在立项阶段即锁定以下度量口径，作为验收与后评估的基线。

表 2 无纸化价值度量基线（以 100 人、每月 30 场、每场 60 页材料的中型单位测算）

| 指标 | 纸质方式基线 | 本系统目标值 | 度量方式 |
| 单场材料印制成本 | 约 60 页 × 100 份，含打印耗材与装订 | 归零，仅保留 1 份存档打印 | 财务单据对比 |
| 会前材料分发耗时 | 2 小时至 1 个工作日 | 3 分钟内完成推送与预载 | 系统日志时间戳 |
| 材料改版响应 | 重新打印，平均 40 分钟 | 30 秒内全端生效 | 版本替换事件记录 |
| 会后纪要成稿 | 4 小时至 2 个工作日 | 会议结束后 30 分钟内生成初稿 | 纪要签发时间 |
| 材料回收与销毁 | 人工清点，易遗漏 | 会议结束即权限回收，终端缓存自动清除 | 审计流水核验 |

## 2.4 能力边界

必须明确本系统不做的事情，否则需求会无限膨胀。本系统不承担会议扩声与话筒表决硬件的底层协议实现，只通过协议适配层对接；不承担视频会议的多方音视频混流，只提供与主流视频会议系统的单点对接；不承担电子签章的法律效力认定，签章能力以第三方 CA 或单位既有签章平台为准；不承担互联网侧的开放公网发布，默认部署在单位内网或专网。

# 3 系统定位与业务蓝图

## 3.1 产品组成

本系统由七部分组成：服务端集群（业务服务、同步服务、媒体与转码服务）、边缘接入网关、PC 客户端、平板终端、一体机终端、白板终端、网页与 TV 端。六端不是六个独立产品，而是同一套会话协议与渲染内核在不同硬件形态上的适配结果。这一定位直接决定了后文的架构：状态集中在服务端，终端只负责呈现与输入。

## 3.2 会议全流程

表 3 会议三阶段与系统动作

| 阶段 | 业务动作 | 系统承载 | 产出数据 |
| 会前 | 建会、编排议程、上传材料、审签、设定参会人与权限、推送预载、发送通知 | 会议服务、材料服务、通知服务 | 会议实体、议程表、材料版本、参会名单、预载回执 |
| 会中 | 签到、开启会议、同屏跟随、批注、表决、临时材料分发、白板协作、设备控制 | 同步服务、白板协同、设备服务 | 签到记录、视口事件、笔迹与批注、表决结果、设备状态 |
| 会后 | 生成纪要、决议与任务、材料归档、缓存销毁、数据上报 | 纪要服务、归档与审计 | 纪要文档、任务清单、归档快照、审计流水 |

## 3.3 扩展场景

系统的核心模型是“受控材料 + 受控议程 + 受控参与者”，因此可低成本扩展到四类场景：一是无纸化评审，把议程换成评审项，把表决换成评分；二是无纸化培训，把同屏换成课件跟随，把签到换成答题；三是无纸化办公，把会议实体换成审批单，材料换成附件；四是远程列席，把网页端换成零信任接入的只读席位。扩展时只允许新增业务插件，不允许修改同步内核。

## 4.3 终端选型理由

PC 端采用 Electron 而非纯 Web，原因是政企环境需要读取本地文件、调用系统截屏接口施加水印、控制双屏输出、与本地打印和签章控件交互，纯浏览器无法满足。平板、一体机、白板统一采用 Capacitor 原生壳加共享内核，原因是这三类硬件本质都是 Android 设备，原生壳解决唤醒、常亮、Kiosk、串口与升降控制，共享内核解决业务一致性。网页端与 TV 端只做纯 Web，原因是它们的使用者是临时列席者与大屏，安装成本高于功能收益。

# 6 企业级开发标准

## 6.1 过程模型与里程碑

开发过程采用“增量迭代 + 阶段评审门”的混合模型，参考 GB/T 8566 的生存周期过程划分，把项目切成六个阶段，每个阶段设硬性出口条件，不满足不得进入下一阶段。

表 8 阶段与出口条件

| 阶段 | 主要活动 | 出口条件 |
| 立项与概念 | 场景调研、可行性、规模测算 | 立项报告通过，目标指标锁定 |
| 需求 | 需求获取、用例、需求规格 | 需求基线冻结，评审无阻断项 |
| 设计 | 概要设计、详细设计、接口定义 | 架构评审与接口评审通过，ADR 归档 |
| 开发 | 编码、单元测试、联调 | 单元测试覆盖率达标，静态扫描零阻断 |
| 测试 | 集成、性能、兼容、安全 | 遗留缺陷等级与数量在阈值内 |
| 交付 | 部署、试运行、培训、验收 | 验收测试通过，运维移交完成 |

迭代周期为两周，每迭代交付可运行增量。跨迭代不合并未完成的功能分支，未完成需求回退到需求池而不是“带病上线”。

## 6.2 需求管理

需求必须带编号入库，格式为 FR-模块-序号（功能需求）与 NFR-类别-序号（非功能需求）。需求变更走三步：变更申请说明影响面，架构师评估对接口与数据模型的影响，产品经理更新基线并通知测试。基线冻结后新增需求一律进入下一版本，不允许在开发中期口头插队，这是工期失控的首要原因。

## 6.3 设计与架构决策

任何跨模块的技术选择必须写 ADR，一条 ADR 包含背景、候选方案、决策、后果与失效条件。本系统的关键决策已固化为 ADR-001 至 ADR-008，见第 10 章。ADR 一旦生效，改动需新开 ADR 并注明替代关系，不允许直接修改历史记录。

## 6.4 编码规范

服务端统一使用 TypeScript 严格模式，禁止 any 逃逸；前端共用同一套 ESLint 与 Prettier 配置，配置放在仓库根目录，各子包继承而不复制。以下条款为强制项。

- 命名：类与接口用大驼峰，方法与变量用小驼峰，常量用全大写加下划线，数据库字段与接口字段用小写下划线，事件名用“域.动作”点分形式。
- 异常：业务异常统一抛领域异常类，禁止用字符串抛错；对外错误码必须来自第 7 分册的错误码表，禁止临时编造。
- 日志：使用结构化 JSON 日志，必须包含 traceId、tenantId、meetingId、terminalId 四个关联字段；禁止打印材料正文与个人敏感信息。
- 时间：服务端一律存 UTC 时间戳，展示层按终端时区转换；禁止在代码中硬编码时区偏移。
- 数值：金额与时长禁止使用浮点累加，统一用整数最小单位或 Decimal。

```typescript
// 统一的结果与异常约定（节选）
export class DomainError extends Error {
  constructor(
    readonly code: ErrorCode,
    readonly message: string,
    readonly httpStatus = 400,
    readonly details?: Record<string, unknown>,
  ) {
    super(message);
  }
}

// 控制器只做参数校验与编排，业务规则下沉到领域服务
@Controller('meetings')
export class MeetingController {
  constructor(private readonly meetings: MeetingService) {}

  @Post(':id/start')
  @RequirePermission('meeting:control')
  async start(@Param('id') id: string, @CurrentUser() user: Principal) {
    return this.meetings.start(id, user); // 抛 DomainError 由全局过滤器转错误码
  }
}
```

## 6.5 分支与提交规范

采用主干开发加短生命周期特性分支的策略：main 恒可发布，release 分支只在发版冻结期存在，hotfix 从 tag 拉出并回合主干。分支命名 feature/模块-简述、fix/问题号-简述、hotfix/版本-简述。

提交信息采用约定式提交，格式为“类型(范围): 描述”，类型限 feat、fix、refactor、perf、docs、test、build、ci、chore。合并请求必须关联需求编号或缺陷编号，必须通过质量门，必须至少一名非作者的模块负责人评审。

```text
feat(sync): 支持按 rev 增量补拉视口事件
fix(document): 修复 300 页 PDF 转帧时内存不释放
docs(api): 补充表决接口的错误码 4207
```

## 6.6 质量门

质量门由流水线自动执行，任一红线不通过则阻断合并。阈值如下，数值为本项目实测基线，不得随意放宽；确需放宽须由架构师书面批准并在迭代回顾中记录。

表 9 质量门阈值

| 检查项 | 工具 | 通过阈值 |
| 单元测试行覆盖率 | Vitest + c8 | 核心领域模块不低于 80%，其余不低于 60% |
| 静态扫描阻断问题 | ESLint + SonarQube | 阻断级为 0，严重级不超过 5 且必须有处置计划 |
| 依赖漏洞 | npm audit + Trivy | 高危为 0，中危须有评估结论 |
| 接口契约一致性 | OpenAPI 校验 | 实现与契约不一致项为 0 |
| 数据库迁移可逆性 | 迁移脚本检查 | 每个迁移必须有对应回滚脚本 |
| 性能基线 | k6 压测 | 同屏同步 P95 不超过 300 毫秒，错误率不超过 0.1% |

## 6.7 版本与发布

版本采用语义化版本 主.次.修订。主版本变更表示接口或数据模型不兼容；次版本表示新增向后兼容能力；修订表示修复。发布采用灰度策略：先在测试会议室与试点单位放量 5%，观察 24 小时的关键指标后放量至 30%，再全量。每次发布必须准备回滚方案，回滚时间目标不超过 15 分钟，数据库变更必须与代码解耦，先加列后删列，禁止同版本内做破坏性字段变更。

## 6.8 配置与密钥管理

配置分四级：镜像内默认配置、环境变量、配置中心（按租户下发）、数据库动态配置。优先级由低到高。所有密钥禁止进入代码仓库与镜像，统一由密钥管理系统注入；国密私钥存放于密码机或加密卡，业务进程只持有句柄。配置文件变更同样需要走变更单，不允许运维直接在服务器上手改。

## 6.9 交付物清单

每个版本交付物包括：源代码与镜像、数据库迁移脚本、部署清单与编排文件、接口契约文件、本套 8 册文档的当前版本、测试报告、安全扫描报告、验收记录。缺项不得归档。

# 10 关键架构决策

本章汇总已生效的架构决策，作为全套文档的约束条件。每条决策的详细论证见对应分册。

表 14 架构决策清单

| 编号 | 决策 | 核心理由 | 失效条件 |
| ADR-001 | 状态集中在服务端，终端只呈现与输入 | 六端一致性与审计可追溯的前提 | 完全离线且无边缘网关的极端场景 |
| ADR-002 | 同屏采用文档级同步而非视频流 | 带宽降低两个数量级，画质无损 | 需要同步第三方实时画面时 |
| ADR-003 | 实时通道采用自研 JSON 事件协议而非通用消息中间件 | 可控的定序、鉴权与降级策略 | 需要与外部系统大规模互通时 |
| ADR-004 | 服务端单体分层部署，按模块划分包而非拆微服务 | 中小规模下运维成本更低 | 单租户超过 500 会议室 |
| ADR-005 | 笔迹采用服务端定序加只追加集合，不做全文 OT | 笔迹提交后不可变，无需变换 | 引入可编辑矢量对象 |
| ADR-006 | 材料统一转页帧，源文件仅用于下载与归档 | 渲染一致性优先于保真编辑 | 需要会中编辑原文 |
| ADR-007 | 老设备通过边缘网关与能力降级接入，不改造硬件 | 保护既有投资，缩短交付周期 | 硬件彻底无法联网 |
| ADR-008 | 六端共享一套渲染内核与设计令牌 | 视觉与交互一致，维护成本可控 | 端侧性能差异无法用参数覆盖 |
